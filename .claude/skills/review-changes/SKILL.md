# Review changes

Review everything that is not committed yet and report what should change before it is. This is a review, not a
rewrite: do not edit files unless the arguments contain `fix` (see the end).

## 0. Project rules

Read `AGENTS.md` at the repo root first: it holds the rules this review enforces (sides, network, saves, plot and world
coordinates, the boundaries round other mods, geometry, mixins, cost, code style and workflow). The checks below apply
on top of the general ones; where they are more specific, they win.

If the directory is not a git repository, or has no commits yet, say so and stop: there is nothing to diff against.

## 1. Collect the change set

From the repo root:

```sh
git status --short
git diff HEAD --stat
git diff HEAD
```

`git diff HEAD` misses untracked files, so read every untracked file in full (`git status --short` lists them with
`??`; expand untracked directories with `git ls-files --others --exclude-standard`). For modified files, read enough
of the surrounding code to judge the change in context, not just the hunks. Skip binary files (images, audio) but
note whether they were regenerated by a script.

## 2. Mechanical checks

Run these and treat any failure as a finding:

- **Build:** `./gradlew build --console=plain`. Report compiler errors and new warnings in changed files.
- **Generated assets are reproducible:** if a script in `tools/` or the files it writes changed, rerun
  `node tools/generate_textures.mjs` and `node tools/generate_resources.mjs` (with the extracted vanilla client
  resources if the change touches the door or call button files, see docs/building.md), then `git status --short` again.
  Any file that changes because of the run means a generated file was edited by hand, or the script and its output
  disagree. Leave the regenerated files in place and report it. `node tools/generate_sounds.mjs` needs rerunning only
  when it changed itself; its output is not byte-for-byte reproducible.
- **Moving things:** these print nothing, or each hit is justified in the report:
  `git grep -nE 'getGameTime\(\)[^;]*[pP]artial' -- src/main/java`, which is the snap-back under server lag, and
  `git grep -nE 'float [a-zA-Z]+ = [^;]*(getGameTime\(\)|getBlockPos\(\)\.get[XZ])' -- src/main/java`, which is a time or
  plot coordinate in a float (a difference of two whole times is fine). In the diff, also look for `sync()` or
  `sendBlockUpdated` on a path that runs every tick while something moves, and for a client's count overwritten from
  saved data without `ToldTicks`.
- **Models on their textures:** with `tools/` or a model in the change set, run this; it prints nothing when every
  face past its block has a `uv` on its texture:
  `node -e 'const fs=require("fs"),p=require("path"),d="src/main/resources/assets/skyliners/models";const u={down:(f,t)=>[f[0],16-t[2],t[0],16-f[2]],up:(f,t)=>[f[0],f[2],t[0],t[2]],north:(f,t)=>[16-t[0],16-t[1],16-f[0],16-f[1]],south:(f,t)=>[f[0],16-t[1],t[0],16-f[1]],west:(f,t)=>[f[2],16-t[1],t[2],16-f[1]],east:(f,t)=>[16-t[2],16-t[1],16-f[2],16-f[1]]};for(const s of fs.readdirSync(d)){for(const n of fs.readdirSync(p.join(d,s))){const m=JSON.parse(fs.readFileSync(p.join(d,s,n)));for(const e of m.elements??[])for(const[k,f]of Object.entries(e.faces)){const v=f.uv??u[k](e.from,e.to);if(Math.min(...v)<0||Math.max(...v)>16)console.log(s+"/"+n,k)}}}'`
- **Lang keys:** every `Component.translatable("...")` key and every registered block, item and entity in the diff has
  an entry in `assets/skyliners/lang/en_us.json`, and no key in the diff is left unused. The lang file is generated:
  a new key must be in `tools/generate_resources.mjs`, not only in `en_us.json` (the generator run above shows it).
- **Protocol version:** if a payload's fields or stream codec changed (any record with a `STREAM_CODEC` registered in
  `Skyliners.onRegisterPayloads`), the version string in `event.registrar("<n>")` went up.
- **Version bump:** if code or assets changed, `mod_version` in `gradle.properties` must go up to a new pre-release
  before the build is handed out. It goes in its own `chore(release)` commit straight after the change, so a missing
  bump in the change set is a note for the commit split, not a defect.
- **Docs:** a change a player can see (a block, an item, a screen, a setting, how something behaves) is described in
  `docs/guide.md` as it now is, and in `README.md` where its short tour mentions it, and `docs/building.md`'s notes
  on which class does what still hold.

## 3. Review

Go through the diff for each of the four areas below. Report only real problems with a concrete reason, not
style preferences the surrounding code does not share.

### Correctness
- Logic errors, off-by-one, wrong sign or axis (model space vs world space; in Minecraft, yaw 0 faces +z).
- **Side safety:** game logic runs only on the server (`level.isClientSide` / `instanceof ServerLevel` checks);
  client-only state is never read on the server, and common code never loads client classes (anything in `client/`,
  `net.minecraft.client.*`, Veil's renderers).
- **Plot and world coordinates:** aboard an assembled airliner, block positions, block entities and hit locations are
  in the Sable plot, while players and entities are in the world. Every comparison or distance between the two goes
  through `SableFlight.toWorld`/`toPlot`/`turnToPlot` (server) or `SableClient.toWorld` (client). A distance from a
  block to a player taken without converting is a bug; so is a direction from the world used on blocks without
  `turnToPlot`.
- **Network payloads:** every client-to-server payload re-validates on the server (block type at the position, reach
  distance, clamped values). A change to a payload's wire format bumps the protocol version.
- **Persistence:** NBT (or any saved format) read and write match field for field. Data saved by the previous
  release still loads (missing keys get a sensible default; enums go by name with a fallback, never by ordinal). Block
  state properties added to an existing block are acceptable only if old worlds still map to a valid state. A block
  entity's state that clients draw is sent with `getUpdateTag`/`getUpdatePacket` and `sendBlockUpdated`.
- Entities and block entities: sensible sizes, tracking range and update interval; nothing left behind on removal
  (sounds, tasks, chunk tickets, entries in a `Loaded<T>` or a saved data); no unbounded per-tick scans.
- **Drawing what moves:** anything turning, sliding or fading on a client goes by `DrawingClock` or its own count, never
  `level.getGameTime() + partialTick`: the server overwrites that about once a second, and it snaps back under lag. An
  angle reaches a `float` only reduced to one turn in a double. Say what the change was measured under: `load server 70`
  in Blockpilot shows a snap-back a frame-by-frame log can count; an idle server shows nothing.
- **Sending what moves:** a block entity tells clients when something changes, not on every tick of a motion they count
  themselves. A full update tag on every tick is both a jitter and a cost.
- Resource leaks and lifecycle: sounds stopped when a screen closes; textures and framebuffers released; long-running
  tasks finish or are dropped with their level.
- **Scale:** airframe geometry and anything measured on the airliner works at every scale (1 to 4), not only the
  default 2.

### Architecture
- The boundaries in `AGENTS.md` hold: Sable only through `SableFlight`/`SableClient` behind `ModList` checks (with the
  two named exceptions), Veil only in `TailCameraFeed`, `VeilLights` and `AdvancedFboImplMixin`, other mods' blocks
  only by registry id through `SkylinersConfig` and `AirframePalette`, client code only in `client/`.
- Airframe geometry is drawn in `AirframeShape`'s metres in the layout's nose-north frame and turns with
  `AirframeBuild.Placement`; block entity data set at build time goes through a `Fitting`; nothing writes world-space
  data in the layout. `CabinFitOut` never cuts into the hull, doors or door aisles (but the moon pool's glazing), and
  hull features go in before the shell pass. New airframe blocks are in `#sable:super_light`.
- Mixins only mend another mod's bug no API reaches, live in `dev.skyliners.mixin`, and are listed in
  `skyliners.mixins.json`.
- New code lands in the package that matches its role, reuses existing helpers instead of copying them (`Loaded`,
  `Turning`, `Fitting`, `Sight`, `ScreenDrawing`, `PanelArt`, `MapPainter`, ...), and does not duplicate logic that
  already exists elsewhere in the diff or the codebase.
- A model with a part past its block is written through the generator's `write`, so its faces stay on their textures; a
  part above its block in a block with a full collision shape sets `ambientocclusion: false`, or it draws black aboard.
- Tunable numbers are named constants with a comment saying what they mean and in what unit, not literals buried in
  logic.
- Assets that a tool generates are changed in the tool, never edited by hand.
- An experimental behaviour sits behind a config switch that defaults to off.

### Quality
- Names say what things are in the game; no misleading leftovers from an earlier design (comments, field names or
  javadoc that describe behaviour the code no longer has, such as a class comment still naming one camera after the
  class learnt to show four).
- Methods do one thing. Loops and ifs nest at most two deep in a method: deeper nesting is a Should fix, flattened by
  extracting a helper or returning early. No multi-statement lambdas inside calls.
- Comments match the codebase's density and voice: javadoc on classes and non-obvious members in plain descriptive
  English with British spelling, saying what a thing is and *why*; no narration of what the next line does. Comments
  wrap at 120 columns.
- Every cue a player needs also has a picture, colour or sound, not text alone: some players cannot read yet.
- `docs/guide.md` describes the behaviour as it now is.

### Hygiene
- No unused imports, fields, methods, constants, lang keys, textures or models; nothing left over from removed
  features.
- No debug output, commented-out code, temporary test helpers (such as an `/aptest` command), TODOs without an owner,
  or stray files (scratch scripts, logs, jars, dev worlds).
- Formatting matches the surrounding code (indentation, line length).

## 4. Report

Lead with a one-line verdict: ready to commit, or not and why. Then list findings ranked by severity:

1. **Blocking**: wrong behaviour, crashes, data loss, client/server violations, protocol or save breakage.
2. **Should fix**: architecture and quality problems that will cost later.
3. **Nits**: hygiene and small polish.

Each finding gives `path:line`, what is wrong, why it matters and the suggested fix, in a sentence or two. Group
findings by file only when there are many in one file. Finish with what was checked mechanically (build,
regeneration, lang keys, protocol version, mod version, docs) and the result of each. If nothing is wrong in an
area, say so in one line rather than padding the report.

Then say what the change still needs checked in game that the build cannot show (rendering, layout and fit-out in a
freshly built airliner, flight behaviour in flight), or that it needs none.

If the change set splits naturally into several commits, suggest the split (one atomic commit per fix or feature,
Conventional Commits subjects, the version bump in its own `chore(release)` commit after them), but do not commit.

## Fix mode

If the arguments contain `fix`, apply the Blocking and Should fix findings after reporting them, plus nits that
are unambiguous. Then rebuild and repeat the mechanical checks. Report what was changed and anything left
undone. Never commit.
