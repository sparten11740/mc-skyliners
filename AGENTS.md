# Aerolarge: notes for coding agents

A NeoForge 1.21.1 mod (Java 21): an A380-style double-deck airliner big enough to build in, assembled into a flying
body by Sable (Create Aeronautics) and flown from its own cockpit, mostly by its autopilot. `README.md` describes every
feature as a player meets it, and its Building section says which classes do what.

## Build and run

- `./gradlew build` writes `build/libs/aerolarge-<mod_version>+1.21.1-neoforge.jar`. There are no unit tests: the build
  is the automated check, and behaviour is checked in game (see Testing in the dev client).
- `./gradlew runClient -PquickPlayWorld=<save>` loads straight into `run/saves/<save>`. Create, Sable, Create
  Aeronautics and Create Propulsion go in `run/mods`. `run/` (worlds, logs, options) is not committed.
- Assets are generated by `tools/`: `node tools/generate_textures.mjs` (textures), `node tools/generate_resources.mjs
  [<extracted vanilla client resources>]` (blockstates, models, loot tables, tags, recipes and `lang/en_us.json`), and
  `node tools/generate_sounds.mjs` (FFmpeg; the flight deck's voice needs Kokoro, installed with `npm install --prefix
  tools`, and air traffic control Windows' speech synthesis). Change the generator, never the file it writes: a new
  lang key goes into `generate_resources.mjs`. Rerunning the generators leaves `git status` clean.

## Where things are (`src/main/java/dev/aerolarge`)

- Root: `Aerolarge` (registration, server ticks, network payloads and their protocol version), `AerolargeClient`,
  `AerolargeRegistry`, `AerolargeConfig` (server config) and `AerolargeClientConfig` (client config), commands.
- `airframe/`: the airliner itself. `AirframeShape` holds the A380's measurements in metres, `AirframeLayout` cuts them
  into blocks nose north, `AirframeBuild` places the result with one rotation, and the fit-out classes (`CabinFitOut`,
  `UpperDeck`, `HoldFitOut`, `CrewRooms`, ...) furnish it. `OutsideCamera` places the outside cameras.
- `block/`: blocks and block entities, the autopilot's control head (`AutopilotBlock`) and screen among them, and the
  helpers several blocks share (`Turning`, `Loaded`, `Relays`, `Stowing`, `Control`).
- `autopilot/`: what flies the airliner. `AutopilotBlockEntity` is the control head's block entity and flies (its
  `fly` method), `ControlSurfaces` moves the flaps, `PinLanding` with `RunwaySearch`, `GroundSurvey`, `AirlinerShape`
  and `RunwayCheck` lands near a pin, `Hop` frees a stuck airliner, `Callouts`, `CabinAnnouncements` and `AtcRadio`
  are the flight deck's voice, and `SetAutopilot`, `OpenAutopilotScreen` and `UnstickAirliner` are its screen's
  payloads. The client draws its screens in `client/` (`AutopilotSettingsScreen`, `DestinationMap`,
  `AutopilotScreenRenderer`).
- `client/`: everything that only runs on the client: renderers, screens, maps, the HUD, `SableClient`.
- `compat/`: `SableFlight`, the server's only way into Sable; `PhysicsAssembler`, which works the Physics Assembler
  as a Create deployer does; `Ultrasplosive`.
- `cabin/`, `airport/`, `radar/`, `radio/`, `entity/`, `item/`, `parachute/`, `selfdestruct/`: features by area, each
  with its own payload records.
- `mixin/`: mixins, as a last resort (see below).

## Rules the code keeps

- **Sides.** Game logic runs on the server. Client classes live in `client/` and are never loaded by common code;
  client payload handlers are registered as lambdas so a dedicated server never loads them.
- **Network.** Changing a payload's wire format bumps the protocol version string in `Aerolarge.onRegisterPayloads`
  (`event.registrar("<n>")`), so mismatched builds refuse to connect instead of misreading each other.
  Client-to-server payloads are checked again on the server.
- **Saves.** NBT is read exactly as it is written, and what the last release saved still loads: a missing key gets a
  sensible default, and enums are saved by name and read back with a fallback.
- **Plot and world coordinates.** An assembled airliner's blocks live in a Sable plot, millions of blocks from where it
  flies. Block positions, block entities and block hit locations aboard are in plot coordinates; players and other
  entities are in world coordinates. Convert with `SableFlight.toWorld`, `toPlot` and `turnToPlot` on the server and
  `SableClient.toWorld` on the client. Mixing the two is this codebase's most common bug.
- **Other mods.** Sable is touched only in `compat/SableFlight` (server) and `client/SableClient` (client), each
  behind a `ModList` check. The exceptions are `SableFlight.fitsAboard`, which the client also calls for its own
  player's pose, and `SableFlight.aboard`, which `FrameProtection` calls on both sides. Veil is touched only in
  `TailCameraFeed`, `VeilLights` and `mixin/AdvancedFboImplMixin`. Create Propulsion and Create Aeronautics' Simulated
  and Offroad are named only by registry id in `AerolargeConfig` and resolved in `AirframePalette`. Create and Sable
  are compiled against, never bundled.
- **Geometry.** New airframe geometry is drawn in `AirframeShape`'s metres in the layout's nose-north frame and turns
  with `AirframeBuild.Placement`, never in world coordinates. Block entities that need data once placed get it through
  a `Fitting`, whose offsets turn with the placement. `CabinFitOut` only furnishes open cabin space or replaces cabin
  floor. It never cuts into the hull, doors or door aisles; the moon pool, which glazes the belly before the shell pass,
  is the one exception. Hull features go in before `AirframeLayout.shell()`. Airframe blocks are tagged
  `#sable:super_light`.
- **Mixins** only mend another mod's bug that no API reaches. They live in `dev.aerolarge.mixin` and are listed in
  `aerolarge.mixins.json`, which is not required, so a changed target is skipped with a warning instead of crashing.
- **Cost.** Nothing scans the world every tick without a bound. Loaded block entities are tracked with `Loaded<T>`,
  heavy work is spread over ticks, and renderers leave out what the camera cannot see.
- **Players.** Some players are young children who cannot read yet, so every cue also gets a picture, a colour or a
  sound, never text alone. An experimental behaviour goes behind a config switch that defaults to off.

## Code style

- Java 21, four-space indents. Comments wrap at 120 columns.
- Every class has javadoc, and so does every member whose purpose is not obvious. It is plain descriptive English with
  British spelling (colour, centre, metre), saying what the thing is in the game and why it is so. Read the
  surrounding code and match its voice. No comments narrating the next line.
- Names say what things are in the game (`PinLanding`, `wheelsBelow`, `Contact`).
- A tunable number is a named constant with a comment giving its meaning and its unit.
- Methods nest loops and ifs at most two deep: extract a helper or return early instead. No multi-statement lambdas
  inside calls.

## Workflow

- **Commits** are atomic, one fix or feature each, with Conventional Commits subjects (`feat(autopilot): ...`,
  `fix(cabin): ...`, `docs(readme): ...`, `chore(release): ...`). The body says what changed for the player and why.
- **Review before committing** with the `review-changes` skill (`.claude/skills/review-changes/SKILL.md`; agents
  without skills follow that file as a checklist), and fix what it finds first. In Claude Code, a Stop hook
  (`.claude/settings.json`) asks for this review whenever a session stops with changes not yet reviewed.
- **Versions.** Every build handed out for play-testing gets a new `mod_version` in `gradle.properties`
  (`0.1.0-alpha.N`), in its own `chore(release): bump version to 0.1.0-alpha.N` commit straight after the change. Two
  jars never share a version.
- **README.** A change a player can see updates `README.md` along with it.
- **Verify in game** what the build cannot show: rendering, layout and fit-out (walk a freshly built airliner, looking
  for floating or misplaced blocks), and flight behaviour (in flight). Say plainly what was not verified.

## Testing in the dev client

- Close the client with its window so the world saves. Killing the process loses everything since the last autosave
  (five minutes). `run/options.txt` should have `pauseOnLostFocus:false`, or the world pauses whenever the window
  loses focus.
- `sable info @e` lists the loaded airliners. To find a block of one, summon a marker into its plot:
  `execute positioned <world pos> in_sub_level <uuid> run summon marker`, then read the marker's `Pos`. Reach a plot
  position with `execute positioned <plot pos> out_sub_level <uuid> run tp <player> ~ ~ ~`.
- Target airliners by uuid. Never run `sable teleport` or `sable remove` on `@e`: those hit every sub-level, the
  wheels of Create Aeronautics' vehicles included.
- Stay aboard a flying airliner. One that outruns the loaded chunks round the player unloads where it is.
