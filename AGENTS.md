# Skyliners: notes for coding agents

Create: Skyliners, a NeoForge 1.21.1 mod (Java 21): an A380-style double-deck airliner big enough to build in, assembled
into a flying body by Sable (Create Aeronautics) and flown from its own cockpit, mostly by its autopilot. `README.md` is
the short tour, `docs/guide.md` and `docs/guide/` give the main features, and `docs/building.md` says which classes do
what. Its mod id, packages and commands are `skyliners`. Up to
0.1.0-alpha.216 it was Aerolarge (`aerolarge`), as older commits still call it, and its airliner still flies as
"Aerolarge three eight zero" on the radio.

## Build and run

- `./gradlew build` writes `build/libs/skyliners-<mod_version>+1.21.1-neoforge.jar`. There are no unit tests: the build
  is the automated check, and behaviour is checked in game, by `node tools/playtest.mjs` for what has gone wrong before
  (see Testing in the dev client). It needs the game, so GitHub Actions cannot run it. GitHub Actions
  (`.github/workflows/build.yml`) builds every push to `main` and every pull request, and fails when
  `generate_resources.mjs` would write anything other than what is committed.
- `./gradlew runClient -PquickPlayWorld=<save>` loads straight into `run/saves/<save>`. Create, Sable, Create
  Aeronautics and Create Propulsion go in `run/mods`. `run/` (worlds, logs, options) is not committed.
- Assets are generated by `tools/`: `node tools/generate_textures.mjs` (textures), `node tools/generate_resources.mjs
  [<extracted vanilla client resources>]` (blockstates, models, loot tables, tags, recipes and `lang/en_us.json`), and
  `node tools/generate_sounds.mjs` (FFmpeg; the flight deck's voice needs Kokoro, installed with `npm install --prefix
  tools`, and air traffic control Windows' speech synthesis); `node tools/generate_icon.mjs` draws the mod's icon
  (`docs/icon.png` for the README and CurseForge, and the mod list's logo). Change the generator, never the file it
  writes: a new lang key goes into `generate_resources.mjs`. Rerunning the generators leaves `git status` clean.

## Where things are (`src/main/java/dev/skyliners`)

- Root: `Skyliners` (registration, server ticks, network payloads and their protocol version), `SkylinersClient`,
  `SkylinersRegistry`, `SkylinersConfig` (server config) and `SkylinersClientConfig` (client config), commands.
- `airframe/`: the airliner itself. `AirframeShape` holds the A380's measurements in metres, `AirframeLayout` cuts them
  into blocks nose north, `AirframeBuild` places the result with one rotation, and the fit-out classes (`CabinFitOut`,
  `UpperDeck`, `HoldFitOut`, `CrewRooms`, ...) furnish it. `OutsideCamera` places the outside cameras.
- `block/`: blocks and block entities, the autopilot's control head (`AutopilotBlock`) and screen among them, and the
  helpers several blocks share (`Turning`, `Loaded`, `Relays`, `Stowing`, `Control`).
- `autopilot/`: what flies the airliner. `AutopilotBlockEntity` is the control head's block entity and flies (its
  `fly` method), `ControlSurfaces` moves the flaps, `PinLanding` with `RunwaySearch`, `GroundSurvey`, `AirlinerShape`
  and `RunwayCheck` lands near a pin, `Hop` frees a stuck airliner, `ParkedShips` unloads a parked ship with nobody near
  and brings it back, `Callouts`, `CabinAnnouncements` and `AtcRadio` are the flight deck's voice, and `SetAutopilot`,
  `OpenAutopilotScreen` and `UnstickAirliner` are its screen's payloads. The client draws its screens in `client/`
  (`AutopilotSettingsScreen`, `DestinationMap`, `AutopilotScreenRenderer`).
- `client/`: everything that only runs on the client: renderers, screens, maps, the HUD, `SableClient`.
- `compat/`: `SableFlight`, the server's only way into Sable; `PhysicsAssembler`, which works the Physics Assembler
  as a Create deployer does; `Ultrasplosive`.
- `cabin/`, `airport/`, `radar/`, `radio/`, `entity/`, `item/`, `parachute/`, `selfdestruct/`: features by area, each
  with its own payload records.
- `mixin/`: mixins, as a last resort (see below).

## Rules the code keeps

- **Sides.** Game logic runs on the server. Client classes live in `client/` and are never loaded by common code;
  client payload handlers are registered as lambdas so a dedicated server never loads them.
- **Network.** Changing a payload's wire format bumps the protocol version string in `Skyliners.onRegisterPayloads`
  (`event.registrar("<n>")`), so mismatched builds refuse to connect instead of misreading each other.
  Client-to-server payloads are checked again on the server.
- **Saves.** NBT is read exactly as it is written, and what the last release saved still loads: a missing key gets a
  sensible default, and enums are saved by name and read back with a fallback.
- **Plot and world coordinates.** An assembled airliner's blocks live in a Sable plot, millions of blocks from where it
  flies. Block positions, block entities and block hit locations aboard are in plot coordinates; players and other
  entities are in world coordinates. Convert with `SableFlight.toWorld`, `toPlot` and `turnToPlot` on the server and
  `SableClient.toWorld` on the client. Mixing the two is this codebase's most common bug.
- **Other mods.** Sable is touched only in `compat/SableFlight` (server) and `client/SableClient` (client), each behind
  a `ModList` check. The exceptions are `SableFlight.fitsAboard`, which the client also calls for its own player's pose,
  `SableFlight.aboard`, which `FrameProtection` calls on both sides, and `SableFlight.toWorld`, by which the sky crane's
  `CraneHook` hangs from her winch on clients too and blocks' client-side chimes sound where the block is in flight.
  `mixin/SubLevelHeatMapManagerMixin` mends Sable's own heat map, which sheds what is put back while it floods a ship,
  and `mixin/SubLevelEntityCollisionMixin` its entity collisions, which miss a block's shape reaching past its block.
  Veil is touched only in `TailCameraFeed`, `VeilLights` and `mixin/AdvancedFboImplMixin`. Blockpilot, the
  play-testing client mod, is touched only in `compat/blockpilot`, compiled only when Blockpilot's API is in the local
  Maven repository and reached by name from `compat/Blockpilot` behind a `ModList` check. Create Propulsion and Create
  Aeronautics' Simulated and Offroad are named only by registry id in `SkylinersConfig` and resolved in
  `AirframePalette`; Aeronautics' hot air burner is also named by class, as the `@Pseudo` target of
  `mixin/HotAirBurnerMixin`, which is skipped without it. Create and Sable are compiled against, never bundled.
- **Geometry.** New airframe geometry is drawn in `AirframeShape`'s metres in the layout's nose-north frame and turns
  with `AirframeBuild.Placement`, never in world coordinates. Block entities that need data once placed get it through
  a `Fitting`, whose offsets turn with the placement. `CabinFitOut` only furnishes open cabin space or replaces cabin
  floor. It never cuts into the hull, doors or door aisles; the moon pool, which glazes the belly before the shell pass,
  is the one exception. Hull features go in before `AirframeLayout.shell()`. Airframe blocks are tagged
  `#sable:super_light`.
- **Mixins** only mend another mod's bug that no API reaches. They live in `dev.skyliners.mixin` and are listed in
  `skyliners.mixins.json`, which is not required, so a changed target is skipped with a warning instead of crashing.
- **Drawing what moves.** The server overwrites a client's game time about once a second, so anything drawn from
  `level.getGameTime() + partialTick` snaps back wherever the server runs behind. What moves goes by
  `client/DrawingClock`: `ticks` or `wholeTicks` for what only moves for show, `gameTime` for what keeps time with a
  moment the server named or looks the same to everyone. Common code cannot reach it, so a block entity's method takes
  the time as an argument and an entity counts its own ticks, as `SlideRide` does. Whole-tick checks against a server's
  moment, which nobody sees move, can still read the level's time. A part a client counts itself (a door, a flight of
  stairs) takes the server's count through `ToldTicks` and is not sent it every tick. A `float` holds neither the game
  time nor a plot coordinate (world age, ~2e7): reduce an angle to one turn in a double first, and take a moment from a
  time in a double.
- **Models.** A face past its block with no `uv` reads off its texture into its neighbours in the atlas: the generator's
  `facesOnTheirTextures` brings them back on, and `write` is the only way a model reaches the disk. A part above its
  block can draw black aboard anything assembled under smooth lighting, whatever the block's collision shape (the
  garden bed's posts did): such a model sets `ambientocclusion: false`, as the sprinkler's does, and in a multipart
  blockstate every model does, as the whole block takes it from its first. Compare aboard against the ground when
  looking at one.
- **Cost.** Nothing scans the world every tick without a bound. Loaded block entities are tracked with `Loaded<T>`,
  heavy work is spread over ticks, and renderers leave out what the camera cannot see: Sable draws an assembled ship's
  block entities every frame unless `Sight` or the renderer says otherwise. A stream of particles goes as one message a
  tick that the client draws them from, not a packet each. Anything loaded for good costs for good: a ship with nobody
  near is let go (`ParkedShips`), and Sable's physics shows in a profile only as "unspecified", so `/sable paused true`
  is how to tell its share.
- **Players.** Some players are young children who cannot read yet, so every cue also gets a picture, a colour or a
  sound, never text alone. An experimental behaviour goes behind a config switch that defaults to off.

## Code style

- Java 21, four-space indents. Comments wrap at 120 columns.
- Every class has javadoc, and so does every member whose purpose is not obvious. It is plain descriptive English with
  British spelling (colour, centre, metre), saying what the thing is in the game and why it is so. Read the
  surrounding code and match its voice. No comments narrating the next line.
- Names say what things are in the game (`PinLanding`, `wheelsBelow`, `Contact`).
- A tunable number is a named constant with a comment giving its meaning and its unit.
- Methods nest loops and ifs at most two deep: extract a helper or return early instead. No multi-statement lambdas
  inside calls.

## Workflow

- **Commits** are atomic, one fix or feature each, with Conventional Commits subjects (`feat(autopilot): ...`,
  `fix(cabin): ...`, `docs(readme): ...`, `chore(release): ...`). The body says what changed for the player and why.
- **Review before committing** with the `review-changes` skill (`.claude/skills/review-changes/SKILL.md`; agents
  without skills follow that file as a checklist), and fix what it finds first. In Claude Code, a Stop hook
  (`.claude/settings.json`) asks for this review whenever a session stops with changes not yet reviewed.
- **Versions.** Releases are numbered by semantic versioning from 1.0.0: a fix bumps the patch, a feature the minor
  version. Every build handed out for play-testing gets a new `mod_version` in `gradle.properties`, the coming release's
  number with `-alpha.N` (`1.0.1-alpha.1`, `1.0.1-alpha.2`, ...) until the release itself goes out, each in its own
  `chore(release): bump version to <version>` commit straight after the change. Two jars never share a version.
  Pushing the tag `v<mod_version>` publishes that build: `.github/workflows/release.yml` builds it and uploads it to
  CurseForge as an alpha, beta or release by its version, with Create, Create Propulsion: Simulated and Create
  Aeronautics as required mods. Its notes are the subjects of the `feat` and `fix` commits since the last tag (the
  last release's, for a release), so those subjects are written for players, unless
  `.github/release-notes/<version>.md` gives them written by hand, as for 1.2.0, the first. It needs the repository's
  `CURSEFORGE_TOKEN` secret and `CURSEFORGE_PROJECT_ID` variable.
- **Docs.** `docs/guide.md` and one page for each ship in `docs/guide/` give only the main features, at most a page
  (about 500 words) each, and leave the rest for players to find. A new main feature, or a change to what they say,
  updates them along with it, and `README.md` too where its short tour mentions it.
- **Verify in game** what the build cannot show: rendering, layout and fit-out (walk a freshly built airliner, looking
  for floating or misplaced blocks), and flight behaviour (in flight). Say plainly what was not verified.
- **Play-test script.** A bug found in play gets a check in `tools/playtest.mjs` along with its fix, where one can catch
  it, written as a player would find the fault and seen to fail without the fix. Run the script before a build is handed
  out, and `--all` before a release.

## Testing in the dev client

- `node tools/playtest.mjs` plays what has gone wrong before, in a flat world of its own, with real keys and clicks, and
  says what held: that each ship's stairs can be walked up from the ground, and so on (`--list` shows them all). With no
  dev client running it starts one from the code as it stands, and it exits 1 if any check failed. Anything against the
  clock in a check goes in one Blockpilot script; read a reply with `--json`.
- Close the client with its window so the world saves. Killing the process loses everything since the last autosave
  (five minutes). `run/options.txt` should have `pauseOnLostFocus:false`, or the world pauses whenever the window
  loses focus.
- `sable info @e` lists the loaded airliners. To find a block of one, summon a marker into its plot:
  `execute positioned <world pos> in_sub_level <uuid> run summon marker`, then read the marker's `Pos`. Reach a plot
  position with `execute positioned <plot pos> out_sub_level <uuid> run tp <player> ~ ~ ~`.
- Target airliners by uuid. Never run `sable teleport` or `sable remove` on `@e`: those hit every sub-level, the
  wheels of Create Aeronautics' vehicles included.
- Stay aboard a flying airliner. With nobody aboard she stays loaded in the air but lands by herself, after a minute,
  or after ten seconds with nobody within 920 blocks (280 past where ships are shown, `shipSightRange`).
- Play-test with Blockpilot (github.com/sparten11740/blockpilot-mcp), a client mod that lets an agent drive the game:
  real clicks and keys, screenshots, waits on conditions, the integrated server's commands with their output, and
  the sounds and messages heard. Put its jar in `run/mods`; every start writes the launcher `run/blockpilot/blockpilot`
  (`blockpilot --wait-ready 300 --wait-world "status"`; `help <command>` gives any command's syntax), and it also
  serves MCP (`--mcp`). On macOS start the client in the background after `caffeinate -u -t 3600`, or with the display
  asleep its window cannot open, and close it with `quit`, which saves the world and waits for the game to exit.
  - Aboard an assembled airliner, positions for `use`, `block` and `nbt` are plot positions: find them with
    `sable:find <sub> <block id>` (plain `find` sees only the world's blocks, within the radius it is given, as in
    `find <block id> 128`, and no further than 128). `sable:info <sub> brief` reads pitch, speed, climb and height
    above the ground, and `sample sable:info <sub> brief every 20t x60` records a landing a second at a time.
  - `use <pos>` and `use e<id>` click only once the crosshair rests on the target, and fail with `obstructed <what>`
    when something stands in the way or `out_of_reach`; `any` clicks whatever is in front, naming it as
    `off_target=` when it is not the target, so keep it for the big multi-block panels and never use it on a block
    buried behind others.
  - `server ...` runs as the server console at the player's position, rotation and dimension, so `~`, `@p` and
    `distance=` count from the player, but `@s` matches no one: `server as=player <command>` runs it as the player.
  - Taking off from the autopilot's screen leaves a standing player behind, and an airliner flying away from the
    player is out of the client's sight past 640 blocks. `sable:tp <sub> <block id or *pattern>` puts the player back
    aboard beside the nearest such block straight away, from the server's copy of the airliner, even once the client
    has dropped it; `sable:tp <plot pos>` boards beside a plot position noted before (`sable:find`), which stays put in
    flight.
  - Sneaking and using a block with something in hand uses that instead (a thrust lever pulled back, a button's
    cover shut), and the reply names it as `sneak_item=`: `select` an empty slot first. `use <pos> hold=40t` holds
    the use key down.
  - Each run of the launcher waits for the agent's next step, seconds after the last: anything against the clock
    (arming the self-destruct and pressing it again within its ten seconds) goes in one script, `a; wait 40t; b`.
  - `camera at <pos> look <pos>` and `screenshot 1280 hud=off` photograph what the build cannot show; look at every
    screenshot taken. `option gamma 1` brightens dark spaces, and the reply says `inside` when the camera is in a
    solid block.
  - Skyliners gives Blockpilot commands of its own (`help skyliners`): `skyliners:build
    airliner|furnished|zeppelin|furnished_zeppelin|festive_zeppelin` lays one down in front of the player and waits
    until it stands; `skyliners:autopilot fly|land|off [altitude=] [speed=] [heading=] [pin=x,z] [land=]` sets the
    nearest autopilot as its screen would, assembling first; and `skyliners:zeppelin` reads a zeppelin's flight (phase,
    height, climb, speed, pitch, heading, mass, each cell's burner signal, the engines, what its pilot has learnt), to
    `sample` through a flight. `skyliners:assembly`, before a zeppelin first flies, counts the blocks its assembly takes
    along and names those of its own it would leave behind, touching the rest only along an edge or not at all, and the
    other blocks pressed against it that would hold it as it flies off: a layout should leave none. `skyliners:layout
    <what>` lays an airframe out without building it and gives its block count and a fingerprint of its blocks: a
    refactor of a layout that should move no block leaves both as they were. `skyliners:livery <name>` repaints the
    nearest zeppelin as its livery board does. `skyliners:dark [radius=] [least=]` counts the spots round the player
    inside the mod's ships, shut off from the sky, that someone could stand in and that are lit less than the least
    (`unlit` counts those with no light, where monsters spawn). A zeppelin's control head is in its control car under
    the bow.
